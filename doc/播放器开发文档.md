# 基于 Qt + FFmpeg 的高性能本地视频播放器开发实战指南

## 项目概述

本项目旨在开发一款基于 C++、Qt 6 框架与 FFmpeg 8 音视频处理库的高性能本地视频播放器。项目采用自顶向下的模块化设计思路，核心难点在于底层音视频流的解封装、解码机制以及多线程环境下的音视频同步渲染。

---

## 第一阶段：系统架构设计 (全局视角)

本播放器采用经典的分层设计思路，确保各个模块之间的低耦合与高内聚：

* **UI 展示层 (View)：** 负责与用户交互，包括视频渲染区域、进度条、播放/暂停控制按钮等（基于 Qt Widgets 实现）。
* **业务控制层 (Controller)：** 响应用户操作，统筹底层解码线程，控制媒体的播放、暂停、快进/快退逻辑。
* **核心解码层 (Model)：** 隐形的“引擎”，负责打开媒体文件、分离音视频流、将高度压缩的数据解码为原始数据（基于 FFmpeg 核心库实现）。
* **渲染输出层：** 负责将解码后的原始图像高效绘制到屏幕上，并将音频采样数据推送到系统扬声器。

---

## 第二阶段：前端 UI 骨架搭建 (所见即所得)

目标是在不考虑底层解码细节的前提下，先把播放器“长什么样”这件事确定下来，并固化为 `.ui` 文件，为后续业务逻辑与解码引擎对接预留好挂载点。

### 2.1 主窗口与布局结构

1. 在 Qt Creator 中新建工程时选择 **Qt Widgets Application**，主窗口基类选择 `QMainWindow`。
2. 在 `QMainWindow` 中，将中央部件替换为一个承载布局的 `QWidget`，并为其设置垂直布局 `QVBoxLayout`：
   - 上半部分预留给“视频渲染区域”；
   - 下半部分用于“控制面板区域”（播放控制条）。
3. 为主窗口与关键控件设置有意义的 `objectName`（如 `mainWindow`、`videoWidget`、`controlPanel`），方便后续在 C++ 代码中通过 `findChild` 或 UI 指针直接访问。

### 2.2 视频渲染区域占位控件

1. 在垂直布局的顶部放置一个占位控件：
   - 初期可以放置 `QWidget` 或 `QLabel`，尺寸策略设置为 `Expanding`，确保窗口拉伸时该区域优先扩展。
   - 背景颜色可以通过样式表暂时设置为黑色 (`background-color: #000000;`)，模拟常见播放器的黑色画面区域。
2. 计划采用 `QOpenGLWidget` 作为最终的渲染控件：
   - 在 UI 骨架阶段，可先放置一个普通的 `QWidget`，后续在 C++ 中通过“控件提升 (Promote to)”机制，将其提升为自定义的 `VideoRenderWidget`（继承自 `QOpenGLWidget`）。
   - 预留该控件的固定最小高度（例如 360 像素），保证即便窗口较小，画面区域仍具备基本可视面积。

### 2.3 控制面板区域 (播放控制条)

1. 在垂直布局底部添加一个 `QWidget` 作为控制面板容器，为其设置水平布局 `QHBoxLayout`。
2. 在该水平布局中依次放置：
   - 播放/暂停按钮：`QPushButton`，文本暂时可设置为 “▶/⏸” 或使用图标资源；
   - 停止按钮：`QPushButton`，文本为 “■” 或“停止”；
   - 播放进度条：`QSlider`（方向设置为 `Horizontal`，拉伸系数设置为 1，使其占据中间的绝大部分空间）；
   - 时间标签：`QLabel`，初始文本设置为 `00:00 / 00:00`，后续由业务层根据媒体时长更新。
3. 为控制面板中的按钮、滑块与标签同样设置明确的 `objectName`（如 `btnPlayPause`、`btnStop`、`sliderPosition`、`labelTime`），方便后续连接信号槽。

### 2.4 所见即所得体验与预留接口

1. 通过 Qt Designer 实时预览布局效果，检查窗口缩放时：
   - 顶部视频区域是否保持居中并优先扩展；
   - 底部控制面板是否保持高度稳定，只在水平方向延展。
2. 在 UI 骨架阶段可以先为按钮绑定一些简单的占位槽函数（例如在状态栏输出调试文本），用于验证交互路径：
   - `void on_btnPlayPause_clicked();`
   - `void on_btnStop_clicked();`
   - `void on_sliderPosition_sliderMoved(int value);`
3. 在主窗口类中预留若干接口或信号，用于与后续的解码/播放引擎进行交互：
   - 发起“打开文件”“开始播放”“暂停/恢复”“停止播放”“请求 seek 到指定位置”等操作；
   - 接收底层引擎发来的“当前播放时间”“总时长变化”“缓冲状态”等通知，驱动 UI 更新。

经过第二阶段，UI 层已经具备完整的外观骨架与基础交互控件，后续只需要在第三阶段开始逐步将这些控件与底层解封装、解码逻辑连接，即可让“静态界面”真正动起来。

## 第三阶段：底层引擎打通 (解封装与获取信息)

本阶段的目标是：封装一个职责清晰的媒体处理类（例如 `VideoDecoder`），负责完成“从文件路径到基础媒体信息”的整条链路，为后续解码与渲染模块提供稳定的数据入口。

### 3.1 初始化 FFmpeg 全局环境

1. 在程序入口或播放器引擎初始化处调用 `av_log_set_level`、`av_log_set_callback` 等接口，根据需要配置日志输出级别，方便后续调试。
2. 在较新的 FFmpeg 版本中通常无需显式注册所有组件，但需要确保正确链接 `avformat` / `avcodec` / `avutil` 等库。

### 3.2 打开媒体文件并完成解封装 (Demuxing)

1. 创建 `AVFormatContext` 指针，并调用 `avformat_open_input` 安全打开本地视频文件：
   - 传入文件路径和媒体格式指针（通常可为 `nullptr`，让 FFmpeg 自动探测）。
   - 对返回值进行错误码判断，出错时通过自定义错误转换函数将 FFmpeg 错误码转为可读字符串，便于 UI 层提示。
2. 调用 `avformat_find_stream_info` 深度读取文件内部信息：
   - 该步骤会遍历部分数据包，用于探测码率、时长、流布局等元信息；
   - 该调用可能较耗时，建议后续考虑放入独立线程中执行，以避免阻塞 UI。

### 3.3 选择音视频流并缓存关键信息

1. 遍历 `AVFormatContext->nb_streams`，从 `AVStream` 数组中找到：
   - 第一个视频流（`codecpar->codec_type == AVMEDIA_TYPE_VIDEO`）；
   - 第一个音频流（`codecpar->codec_type == AVMEDIA_TYPE_AUDIO`）。
2. 分别记录视频流与音频流的 `stream_index`，后续读取 `AVPacket` 时需要用该索引区分包类型。
3. 从视频流的 `AVStream->codecpar` 中提取关键参数：
   - 宽、高 (`width` / `height`)；
   - 编码格式 (`codec_id`)；
   - 帧率（可通过 `avg_frame_rate` 或 `r_frame_rate` 计算得到）。
4. 从 `AVFormatContext->duration` 或音视频流的 `time_base` / `duration` 中计算媒体总时长（转换为秒或毫秒的统一单位）。

### 3.4 将基础媒体信息反馈到 UI 层

1. 在 `VideoDecoder` 类中定义用于承载媒体信息的简单数据结构（例如 `MediaInfo`），包括：
   - 总时长（秒或毫秒）；
   - 分辨率（宽 x 高）；
   - 帧率 (FPS)；
   - 是否包含音频流、音频采样率等。
2. 利用 Qt 信号槽机制，将解析出的 `MediaInfo` 发送给主窗口或控制层：
   - 更新时间标签中的总时长显示；
   - 根据分辨率调整视频渲染区域的显示策略（如保持宽高比）；
   - 为进度条设置最大值（例如总时长对应的毫秒数）。
3. 发生错误时，通过专用错误信号将错误信息上报 UI，让用户明确知道是“文件不存在”“格式不支持”还是“解封装失败”等问题。

完成第三阶段后，播放器已经具备“打开任意本地媒体文件并正确识别其基础信息”的能力，为第四阶段的解码循环提供了可靠的输入前提。

## 第四阶段：核心解码流水线 (压缩数据转原始数据)

本阶段的目标是：在第三阶段“成功打开媒体并获取基础信息”的基础上，进一步完成从压缩码流到原始视频帧 (`AVFrame`) 的连续解码流水线搭建，为后续的格式转换与渲染提供源数据。

### 4.1 初始化解码器上下文

1. 在 `VideoDecoder` 或专门的解码工作类中，为视频流创建 `AVCodecContext`：
   - 通过 `AVCodecParameters* codecpar = videoStream->codecpar;` 获取编码参数；
   - 调用 `avcodec_find_decoder(codecpar->codec_id)` 查找对应的软解码器；
   - 使用 `avcodec_alloc_context3(decoder)` 分配解码上下文。
2. 利用 `avcodec_parameters_to_context` 将 `AVStream` 中的参数拷贝到 `AVCodecContext` 中，确保解码器上下文与媒体文件实际编码参数一致。
3. 调用 `avcodec_open2` 打开解码器：
   - 可以先构造一个 `AVDictionary*` 传入一些可选解码参数（例如线程数、低延迟模式等），也可以传 `nullptr` 使用默认配置；
   - 对返回值进行错误处理，并在失败时通过错误信号反馈给 UI。

### 4.2 构建解码线程与数据读取循环

1. 将解码逻辑放入独立线程中执行（可采用继承 `QThread` 或者在 `QObject` 中使用 `moveToThread` 的方式）：
   - 主线程负责 UI 与控制命令（播放/暂停/停止、seek 等）；
   - 解码线程负责从 FFmpeg 中持续读取数据并解码。
2. 在解码线程中创建一个主循环，例如：
   - 使用 `while (!m_abort)` 作为循环条件，`m_abort` 由外部控制停止；
   - 每次循环调用 `av_read_frame(fmtCtx, packet)` 从文件中读取一个 `AVPacket`。
3. 根据 `packet->stream_index` 判断数据属于视频流还是音频流：
   - 若为视频流，则送入视频解码器；
   - 若后续需要同步解码音频，可为音频流配置独立解码通道。
4. 在遇到 `AVERROR_EOF` 或其他错误码时，合理处理：
   - EOF：可以选择发送一个结束信号，通知 UI 播放完毕；
   - 可恢复错误：适当跳过当前包或延时重试。

### 4.3 将压缩数据送入解码器

1. 为解码准备可重复使用的 `AVPacket` 实例，避免在循环中频繁分配和释放内存：
   - 使用 `av_init_packet` 或 `av_packet_alloc` 初始化；
   - 每次 `av_read_frame` 成功后，将获取的数据包直接送入解码器。
2. 调用 `avcodec_send_packet(codecCtx, packet)` 发送压缩数据：
   - 如果返回 `AVERROR(EAGAIN)`，说明解码器内部缓冲区未完全消耗，需要先通过 `avcodec_receive_frame` 取出更多已解出的帧；
   - 如果返回严重错误，应当记录日志并根据需要中断播放。
3. 对于不属于当前解码通道的 `packet`（例如音频包暂未处理），需要调用 `av_packet_unref(packet)` 及时释放内部引用，避免内存泄漏。

### 4.4 拿到解码后的原始视频帧

1. 在成功 `send_packet` 之后，进入一个内部循环，不断调用：
   - `int ret = avcodec_receive_frame(codecCtx, frame);`
   - 使用事先分配好的 `AVFrame* frame` 缓冲每一帧解码结果。
2. 根据返回值处理不同情况：
   - `ret == 0`：成功拿到一帧原始视频数据，将其压入自定义帧队列，等待渲染阶段消费；
   - `ret == AVERROR(EAGAIN)`：表示解码器暂时没有更多可取的帧，需要等待下一次送入新包后继续；
   - `ret == AVERROR_EOF`：表示解码器内部缓存已完全输出，解码流程可以进入收尾阶段。
3. 对于拿到的每一帧，记录其关键时间戳：
   - 使用 `frame->pts` 结合流的 `time_base` 计算出该帧的展示时间（单位可统一为毫秒）；
   - 后续的音视频同步逻辑会以这个时间戳为核心数据之一。

### 4.5 资源管理与异常收尾

1. 保证在解码线程退出前，依次释放或关闭所有与解码相关的资源：
   - 调用 `avcodec_free_context` 释放 `AVCodecContext`；
   - 调用 `av_frame_free` 和 `av_packet_free` 释放循环复用的 `AVFrame` 与 `AVPacket`；
   - 调用第三阶段已经实现的 `close()` 接口关闭 `AVFormatContext`。
2. 在解码过程中出现异常（文件损坏、读盘错误等）时：
   - 通过 Qt 信号将错误信息上报给主线程；
   - 安全终止解码循环，避免死循环或崩溃。

经过第四阶段，播放器已经能够稳定地将压缩视频流转换为连续输出的原始视频帧序列，为第五阶段的色彩空间转换与渲染打下了完整的数据基础。

## 第五阶段：格式转换与画面渲染 (让画面动起来)

本阶段的目标是：将第四阶段得到的原始视频帧 (`AVFrame`，通常为 YUV 色彩空间) 转换为 Qt 可直接渲染的 RGB 图像，并构建一条稳定的“解码线程 → 渲染线程（UI 主线程）”的图像传输与重绘通路。

### 5.1 规划渲染组件与数据通路

1. 在 UI 层为视频区域创建专用渲染控件，例如 `VideoRenderWidget`：
   - 继承自 `QOpenGLWidget` 或 `QWidget`；
   - 提供一个公开接口 `setFrame(const QImage& frame)`，用于接收最新帧；
   - 在 `paintEvent` 中使用 `QPainter` 将内部缓存的 `QImage` 绘制到控件区域内，必要时保持宽高比。
2. 在 `VideoDecoder` 与渲染控件之间约定信号/槽：
   - `VideoDecoder` 在解码完成并完成色彩转换后发出信号，例如 `videoImageReady(const QImage& image, qint64 ptsMs)`；
   - 主窗口或控制层中转该信号，将 `QImage` 传递给 UI 线程中的 `VideoRenderWidget::setFrame`，并触发控件的 `update()`。

### 5.2 构建 swscale 色彩转换上下文

1. 针对视频解码器输出的像素格式，创建 `SwsContext`：
   - 在成功打开解码器并获得视频宽高、像素格式 (`videoCodecCtx->pix_fmt`) 后，调用
     `sws_getContext(srcW, srcH, srcPixFmt, dstW, dstH, dstPixFmt, SWS_BILINEAR, nullptr, nullptr, nullptr)`；
   - 其中目标像素格式可选 `AV_PIX_FMT_RGBA` 或 `AV_PIX_FMT_BGRA`，方便与 Qt 的 `QImage::Format_RGBA8888`、`QImage::Format_ARGB32` 对应。
2. 将 `SwsContext` 作为 `VideoDecoder` 的成员，避免每帧重复创建：
   - 在分辨率变化或像素格式变化时，重新初始化该上下文；
   - 在关闭解码器时调用 `sws_freeContext` 释放资源。

### 5.3 将 AVFrame(YUV) 转为 RGB 缓冲区

1. 在解码线程中，当 `avcodec_receive_frame` 得到一帧原始视频数据后：
   - 准备一块用于存储 RGB 数据的缓冲区，可以采用：
     - 预先分配一帧大小的连续内存（`dstBuffer`），配合 `AVFrame* rgbFrame` 与 `av_image_fill_arrays` 管理行指针；
     - 或每次根据宽高动态 `av_image_alloc`，解码结束后释放。
2. 调用 `sws_scale` 完成逐行色彩转换：
   - 源数据为解码得到的 `frame->data` 与 `frame->linesize`；
   - 目标为 `rgbFrame->data` 与 `rgbFrame->linesize`；
   - 遍历高度 `srcH` 完成整帧转换。
3. 转换完成后，得到一块连续的 RGB 像素数据，可直接用于构造 `QImage`：
   - 注意保持与 Qt 像素格式匹配（例如行对齐、字节顺序）。

### 5.4 将 RGB 像素封装为 QImage

1. 在解码线程中构建 `QImage` 可能会跨线程访问 Qt GUI 类型，建议采用数据与 GUI 分离的方式：
   - 解码线程只负责提供原始 RGB 缓冲区的拷贝（例如使用 `QByteArray` 或自定义结构包装），然后通过信号发送到 UI 线程；
   - 在 UI 线程中，再将该缓冲区封装为 `QImage` 对象。
2. 若选择直接在解码线程中创建 `QImage`：
   - 需要确保 `QImage` 的使用是线程安全的：通常做法是
     - 使用“深拷贝”构造函数 (`QImage` 会拷贝一份自己的缓冲区)，
     - 然后通过信号槽的 Qt::QueuedConnection 将 `QImage` 拷贝传递到主线程。
3. 为了减少拷贝次数，可以在 `VideoRenderWidget` 内部采用“纹理上传”的方式（配合 `QOpenGLTexture`），但在文档阶段可先以 `QImage` 为主要承载类型。

### 5.5 触发界面重绘与线程边界处理

1. 使用 Qt 信号槽机制跨线程传递图像数据：
   - 在 `VideoDecoder` 中发出 `videoImageReady(QImage image, qint64 ptsMs)` 信号；
   - 在主窗口中连接到渲染控件的槽，例如 `VideoRenderWidget::setFrame`；
   - 由于默认连接类型在跨线程时为 `QueuedConnection`，Qt 会自动将调用投递到 UI 线程执行。
2. 在 `VideoRenderWidget::setFrame` 槽函数中：
   - 更新内部的 `QImage` 成员变量（例如 `m_currentFrame`）；
   - 调用 `update()` 请求重绘；
   - 在 `paintEvent` 内根据窗口大小、是否保持纵横比等策略，将图像绘制到控件区域。
3. 结合第四阶段的 PTS 时间戳：
   - 将 `ptsMs` 作为后续第六阶段同步逻辑的输入，为“何时显示这帧”提供参考；
   - 在纯第五阶段阶段，不强制按真实时间呈现，只要能够连续显示帧即可验证渲染链路。

完成第五阶段后，播放器已经具备“解码 → 色彩转换 → QImage 封装 → UI 重绘”的完整视频图像路径，屏幕上可以看到连续更新的画面，为第六阶段进一步引入音视频同步与节奏控制打下基础。

## 第六阶段：多线程与音视频同步 (核心技术难点)

本阶段的目标是：在已经打通“解码 → 渲染”的基础上，引入全局时间轴与同步策略，使画面和声音按真实时间节奏播放，并支持流畅的进度拖动与跳转。

### 6.1 并发模型与线程职责划分

1. 将播放器整体划分为三个主要线程角色：
   - UI 线程：负责界面绘制、用户交互（按钮、进度条、菜单等），所有 `QWidget` 渲染必须在该线程进行；
   - 解码线程：负责从 FFmpeg 读取压缩数据、解码为原始帧，并完成 YUV→RGB 转换；
   - 音频播放线程（或音频回调）：负责将音频数据送入音频设备，充当“主时钟”。
2. 在代码结构上：
   - 将当前 `VideoDecoder` 解码逻辑通过 `moveToThread` 或内部线程管理方式，与 UI 线程彻底解耦；
   - 保证所有跨线程通信均通过 Qt 信号槽完成，避免直接跨线程访问 GUI 对象。
3. 约束原则：
   - 解码线程不得直接阻塞 UI 线程；
   - UI 线程不进行任何重 CPU 的工作（解码、色彩转换等），仅处理轻量逻辑与绘制。

### 6.2 引入主时钟与音视频同步策略

1. 选择音频时间作为全局“主时钟”：
   - 在音频播放模块中，维护一个不断前进的“当前播放时间”变量（单位毫秒），例如 `audioClockMs`；
   - 每当音频缓冲被送入音频设备时，根据样本数、采样率累加时间，或通过音频 API 查询当前播放位置。
2. 在视频渲染路径中使用 PTS 与音频时钟对齐：
   - 对每一帧视频，使用第四/第五阶段已经计算好的 `ptsMs` 作为该帧应显示的目标时间；
   - 在 UI 或渲染调度层比较 `ptsMs` 与 `audioClockMs`：
     - 若 `ptsMs` 远大于当前音频时间（画面“超前”）：适当延时等待，直到接近目标时间再显示；
     - 若 `ptsMs` 明显落后于音频时间（画面“滞后”）：采取丢弃部分视频帧、只显示最新一帧的策略进行追赶。
3. 为简单验证同步机制，可以在尚未加入真实音频播放时：
   - 先以系统时钟 (`QElapsedTimer`) 作为临时时钟替代音频时钟；
   - 模拟“1x 播放速度”，确保进度条与画面刷新大致以正常速度推进。

### 6.3 帧队列与调度器设计

1. 在解码线程与渲染线程之间，引入线程安全的帧队列结构：
   - 解码线程将解出的 `QImage + ptsMs` 压入队列；
   - 渲染调度层从队列中按照时间顺序取出适当的帧进行显示。
2. 队列需要具备基本的容量控制与丢帧策略：
   - 设置最大缓存帧数（例如 30–100 帧），防止解码过快导致内存占用过大；
   - 当队列中过多帧的 `ptsMs` 已经落后于音频时间太多时，批量丢弃这些帧，仅保留最新的几帧用于追赶。
3. 渲染调度可以通过定时器驱动：
   - 在 UI 线程中使用 `QTimer` 定期（例如每 10–20ms）检查当前音频时间与队列头部帧的 `ptsMs`；
   - 根据同步策略决定是否显示该帧、等待、或继续丢弃。

### 6.4 精准 Seek 与进度条交互

1. 当用户拖动进度条到新位置时，将屏幕上的“目标时间”转换为 FFmpeg 的时间戳：
   - 计算目标秒数或毫秒数 `targetMs`；
   - 使用对应流的 `time_base` 将毫秒数转换为 PTS：`targetPts = av_rescale_q(targetMs, AVRational{1,1000}, stream->time_base)`。
2. 调用 `av_seek_frame` 跳转到接近目标位置的关键帧：
   - 先停止当前解码循环，并清空视频帧队列；
   - 对 `AVFormatContext` 调用 `av_seek_frame`，使用 `AVSEEK_FLAG_BACKWARD` 等标志确保从最近的关键帧向后解码；
   - 调用 `avcodec_flush_buffers` 清理解码器内部缓存，避免旧帧混入新位置。
3. Seek 完成后，重新启动解码：
   - 解码线程从新位置开始解码，将新帧推入队列；
   - 渲染调度层根据新的 `targetMs` 更新音频/视频时钟状态，保证画面与进度条立即跳转到用户指定位置附近。

### 6.5 同步效果验证与边界情况处理

1. 验证播放速度与时间一致性：
   - 使用秒表或在界面上显示当前“播放时间”，确认 10 秒现实时间大致对应 10 秒媒体时间；
   - 快速播放、暂停、继续，观察画面和进度条是否保持一致。
2. 测试不同操作场景下的稳定性：
   - 多次快速拖动进度条、频繁点击播放/暂停/停止；
   - 打开长视频、高清高码率视频，观察队列长度和同步表现。
3. 处理异常情况：
   - 当音频轨道缺失或暂未实现音频播放时，使用系统时钟作为替代时钟，并在文档与代码中清晰标注；
   - 在解码或 seek 过程中收到错误（如 I/O 错误），通过统一错误通道通知 UI，并安全停机。

完成第六阶段后，播放器将从“能解、能画”提升到“按节奏播放、可互动控制”的完整形态，具备基本可用的音视频同步与快进/快退体验。

## 第七阶段：倍速播放功能 (时间控制艺术)

本阶段的目标是：在现有的音视频同步框架上，增加变速播放支持（如 0.5x, 1.0x, 1.5x, 2.0x），并保证在变速状态下画面流畅、音调正常（不变声）。

### 7.1 倍速播放的核心原理

1. **视频倍速**：本质上是改变“帧的呈现速度”。
   - 如果原视频 30fps，每帧间隔 33ms。
   - 2.0x 倍速下，每帧间隔应变为 16.5ms，或者主时钟（Audio Clock）走得比真实时间快 2 倍。
   - 渲染循环不需要特殊处理，只需要紧跟主时钟即可。如果主时钟变快，视频帧自然会被更快地取出和显示。

2. **音频倍速 (难点)**：不能简单地加快采样率播放（会导致变声，像“鸭子叫”）。
   - 需要使用 **时间伸缩 (Time Stretch)** 算法，在改变时长的同时保持音高不变。
   - FFmpeg 提供了 `atempo` 滤镜，或者使用 `SoundTouch` / `Sonic` 等第三方库。本项目推荐优先使用 FFmpeg 内置滤镜链。

### 7.2 音频滤镜链 (Filter Graph) 搭建

1. 初始化滤镜图 (`AVFilterGraph`)：
   - 创建 `abuffer`（输入端，接收原始音频帧）和 `abuffersink`（输出端，输出处理后的音频帧）。
   - 中间连接 `atempo` 滤镜，参数设置为当前的倍速值（例如 "2.0"）。

2. 动态调整倍速：
   - 当用户切换倍速时，最简单的做法是销毁并重建滤镜链。
   - 将新的倍速参数传给 `atempo`。
   - 注意：滤镜链重建期间要做好线程保护，避免音频线程读取到空指针。

### 7.3 音频重采样与时钟校准

1. **重采样集成**：
   - 经过滤镜处理后的音频帧，其采样率、格式可能发生微小变化，建议在滤镜输出后再接一个 `swr_convert` 重采样环节，确保输出给声卡的格式始终固定（如 44100Hz, Stereo, S16LE）。

2. **时钟校准**：
   - 音频时钟的计算方式需要适配倍速。
   - 公式：`当前PTS = 上一帧PTS + (本帧样本数 / 采样率) * 速度因子`？
   - **错误**：音频时钟应该直接反映“已经播放了媒体文件的多少秒”，而不是“现实世界过了多少秒”。
   - 因此，无论几倍速，音频时钟依然是：`已播放样本数 / 采样率`。
   - 区别在于：声卡消耗样本的速度变快了（单位时间内喂给声卡的数据量变大了，或者声卡回调频率不变但每次填充的数据代表的时间变长了？不对）。
   - **正确逻辑**：
     - 声卡回调请求数据的速度是不变的（例如每秒消耗 44100 个样本）。
     - 我们通过 `atempo` 滤镜，把“10秒的原始音频”变成了“5秒的输出音频”（2倍速）。
     - 声卡播放这 5 秒数据，现实世界过了 5 秒。
     - 但对于播放器逻辑来说，进度条应该走了 10 秒。
     - 所以：**Audio Clock 依然由当前播放的音频帧 PTS 决定**。只要滤镜正确输出了对应的 PTS，同步逻辑就不需要修改。

### 7.4 界面交互与状态维护

1. **倍速菜单**：
   - 在控制栏添加“倍速”按钮，点击弹出菜单（0.5x, 0.75x, 1.0x, 1.25x, 1.5x, 2.0x）。
   - 记录当前倍速状态 `m_playbackRate`。

2. **即时生效**：
   - 切换倍速时，除了重建音频滤镜，最好也调用一次 `flush`，清空当前堆积的音频缓存，让变速效果立即反馈，减少延迟感。

3. **性能注意**：
   - 高倍速（如 3.0x）意味着解码速度必须跟上 3 倍的消耗速度。
   - 如果解码跟不上，需要有丢帧策略（只解关键帧或丢弃非参考帧），这在第四/六阶段的优化中已经有所铺垫。

## 第八阶段：音频模块集成 (听觉盛宴)

本阶段的目标是：实现音频流的解封装、解码、重采样以及通过声卡播放，并正式启用“音频主时钟”作为全场的同步基准。

### 8.1 音频解码流水线

1. **音频解码器初始化**：
   - 参考视频解码流程，在 `VideoDecoder` 中增加 `audioStreamIndex`、`audioCodecCtx` 的初始化。
   - 打开解码器时，注意检查音频格式（Sample Format, Sample Rate, Channels）。

2. **音频数据读取**：
   - 在主解码循环 (`av_read_frame`) 中，增加对 `packet->stream_index == audioStreamIndex` 的处理分支。
   - 建立独立的 `std::deque<AVFrame*> audioQueue` 音频帧队列，用于缓冲解码后的音频帧。
   - 注意：音频帧通常比视频帧小但数量多，队列容量控制策略需调整（例如按数据时长控制，缓存 1-2 秒数据）。

### 8.2 音频重采样 (Resampling)

1. **为什么要重采样？**
   - FFmpeg 解出的音频格式千奇百怪（如 FLTP, S16P, 48000Hz, 44100Hz 等）。
   - 播放设备（声卡）通常只接受特定的格式（如 S16LE, 44100Hz, Stereo）。
   - 必须在中间加一道转换，确保喂给声卡的数据是它“爱吃”的。

2. **SwrContext 配置**：
   - 初始化 `SwrContext`：
     - 输入参数：取自 `audioCodecCtx` (channel_layout, sample_rate, sample_fmt)。
     - 输出参数：固定为声卡目标参数 (如 AV_CH_LAYOUT_STEREO, 44100, AV_SAMPLE_FMT_S16)。
   - 在音频线程中，每次从队列取出 `AVFrame` 后，调用 `swr_convert` 将其转换为目标格式的 PCM 数据块。

### 8.3 音频输出 (QAudioSink / SDL)

1. **选择音频后端**：
   - 本项目推荐使用 Qt 原生的 `QAudioSink` (Qt6) 或 `QAudioOutput` (Qt5)，与 UI 集成更紧密。
   - 备选方案：SDL2 音频模块（跨平台性能更好，但引入新依赖）。

2. **实现 QIODevice 适配器**：
   - 创建一个继承自 `QIODevice` 的类（例如 `AudioOutputDevice`）。
   - 重写 `readData(char *data, qint64 maxlen)` 方法。
   - 当 `QAudioSink` 需要数据时，会自动回调 `readData`。
   - 在 `readData` 内部：
     - 从 `audioQueue` 中取出解码帧。
     - 执行 `swr_convert` 重采样。
     - 将 PCM 数据填充到 `data` 指针中。
     - 同时更新“音频时钟”：`m_audioClock += (读取样本数 / 采样率)`。

### 8.4 建立音频主时钟 (Master Clock)

1. **校准时钟**：
   - 真正的音频时钟 = `m_audioClock` - `声卡缓冲区延迟`。
   - `QAudioSink` 内部有一定的缓冲，写入的数据不会立刻发出声音，需要扣除这部分延迟（`bytesBuffered() / bytesPerSec`）。

2. **替换系统时钟**：
   - 修改 `VideoDecoder` 或 `MainWindow` 中的同步逻辑。
   - 废弃之前的 `QElapsedTimer` 模拟时钟。
   - 让视频渲染线程直接查询 `AudioOutputDevice` 获取当前准确的音频时间 PTS。

### 8.5 音频倍速适配 (回顾)

1. 结合第七阶段的滤镜链：
   - 将 `atempo` 滤镜插入到解码与重采样之间。
   - 流程更新为：`Packet` -> `Decoder` -> `AVFrame` -> `Filter(atempo)` -> `Filtered Frame` -> `SwrConvert` -> `PCM Buffer` -> `QAudioSink`。

2. 确保同步：
   - 无论倍速如何，音频时钟依然基于“实际输送给声卡的采样数”计算。
   - 视频同步逻辑只需无脑跟随音频时钟，无需感知倍速细节。

完成第八阶段后，播放器将成为真正意义上的“影音播放器”，画面与声音完美同步，且支持变速播放。这是项目最复杂也最核心的里程碑。
